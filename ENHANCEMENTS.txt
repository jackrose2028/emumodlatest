EMULATORJS (LOCAL EDITION): ENHANCEMENTS AND CHANGES FROM THE ORIGINAL EMULATORJS
====================================================================================================

This document lists every change this copy makes to the original EmulatorJS 4.3.0-pre source
(github.com/EmulatorJS/EmulatorJS). The changes were made in five rounds: an efficiency rewrite that
makes everything run from local files, 50 player-facing enhancements, 50 engine improvements, a game
library with its own game page, and a second engine, NostalgistMod (built from Nostalgist.js), that
you can choose instead of EmulatorJSMod. The detailed lists below start with the newest round. A
sixth round, added later, is described in the addendum at the end: 15 performance features in
EmulatorJSMod and the game folders loading in both engines. A seventh round, the second addendum,
makes EmulatorJSMod draw only the game picture into a smaller, whole-number scaled buffer, which
cuts the pixels drawn per frame by about a quarter to two thirds. An eighth round, the third
addendum, makes the drawing surface of the game opaque and, for 2D systems, drops its unused depth
and stencil buffers, so the browser composites less and the graphics chip holds less memory. A ninth
round, the fourth addendum, adds the ObsoleteMod game shelf to the site, running on EmulatorJSMod,
with a new Links page to reach it. A tenth round, the fifth addendum, adds the reference docs (one
page per project file) with a viewer reached from the home page and the Links page. An eleventh
round, the sixth addendum, gives phones and iPhones their own layout that follows rotation, with a
game menu sheet and an on-screen controller for NostalgistMod. A twelfth round, the seventh
addendum, stops the EmulatorJSMod audio processing while a game is paused or hidden and brings
iPhone sound back after interruptions. A thirteenth round, the eighth addendum, adds an in-game save
slot picker with a picture of every save. A fourteenth round reviews the whole site on iPhone and
other phones and fixes what that found, and a fifteenth adds a 2.5D mode for NES and SNES games,
switched on with the 2.5D button on the home page. A sixteenth round asks for the system and core
before any game file opens and reads inside zips, fixing N64 zips that started as arcade games. A
seventeenth round adds a start page with ten use cases (a 10-phase plan in ROADMAP.md), keeps the
previous home page as Basic, and builds phase 1, My Collection. An eighteenth round builds phase 2,
the Homebrew showcase: a page per homebrew game with credits, licence, controls and Play, published
by adding a folder. A nineteenth round builds phase 3, the Museum and exhibit kiosk: an attract
loop, approved games, timed sessions, walk-away resets, a staff PIN and offline play for unattended
public screens. A twentieth round builds phase 4, the Classroom: a running game beside live views of
its palettes, sprites, background, tiles, sound, memory, frames and input, with six 45-minute
lessons and printable worksheets. A twenty-first round builds phase 5, the Web development case
study: a guided tour of how the site is built, with live values, real code excerpts and exercises
that check themselves. A twenty-second round builds phase 6, the Preservation archive: catalogue
records with provenance, licences and checksums verified in the browser, playable in place. A
twenty-third round builds phase 7, Accessible and comfort play: presets and options for speed,
rewind, saving, buttons, touch controls, colour, sound captions and one-switch play. A twenty-fourth
round builds phase 8, Community spaces: a locked-down, low-power launcher with opening hours, volume
limits, turns, fresh saves for each visitor and an offline package. A twenty-fifth round builds
phase 9, Events and speedrun practice: segments with save points, a frame-accurate timer, practice
that shows improvement, full runs with splits and personal bests, shareable save points and two-
player races. A twenty-sixth round builds phase 10, Build your own arcade: one site.json brands
every page, written by a kit page with a live preview and a publishing guide; with it all ten phases
are done. A twenty-seventh round is a second pass on phase 1, My Collection: duplicates by content,
recognised games, shelves, status and notes, own covers, bulk changes with undo, a list view,
keyboard and controller navigation, and exports in parts. A twenty-eighth round is a second pass on
phase 2, the Homebrew showcase: sorting, filters, New badges and author pages; play in place, a
picture viewer, credits, release notes, checksum checks, Add to My Collection, Share and Embed; and
share pages with link previews and a feed when publishing. A twenty-ninth round is a second pass on
phase 3, the Museum and exhibit kiosk: a second visitor language, How to play, a visitor sound
button, opening hours, dimming, a game order, a check of every game, visitor numbers per game and
day, and screens managed from one kiosk.json. A thirtieth round is a second pass on phase 4, the
Classroom: a step-by-step presenter with timers, exit-ticket quizzes, a seventh lesson on binary and
hex, saved moments, watched and changeable bytes, a byte finder, tile bit planes and pictures saved
as PNG. A thirty-first round is a second pass on phase 5, the Web development case study: four new
tour stops, two new exercises, exercise checks that no longer go stale, highlighted code, quiz
scores, a printable handout, and reference docs for every file added since they were first written.

Nothing in this document changes how games are emulated: the same libretro cores (the supplied .7z
files, unmodified) do the emulation. What changed is how the cores and games are found, downloaded,
cached, saved, controlled and presented.

1. OVERVIEW: WHAT IS DIFFERENT AT A GLANCE
====================================================================================================

  - Runs 100% from local files: no CDN, no update check, no external requests. Works on GitHub Pages
    and on any static web server.
  - Uses the core archives exactly as built (<core>[-thread][-legacy]-wasm.7z) and picks the right
    variant from data/cores/manifest.json.
  - Threads work on GitHub Pages: sw.js adds the cross-origin isolation headers that GitHub Pages
    cannot send.
  - Offline support and fast repeat visits through the service worker and the IndexedDB cache.
  - A new home page: drop a ROM (with BIOS and patch), automatic system detection, a game library
    from data folders, recent games, save backup, and help text on every option.
  - A game page with Home link and Platform / Game dropdowns.
  - In-game hotkeys (F1 to F11), controller hotkeys, persistent quick-save slots, resume points,
    auto-pause and more.
  - Save states work with the supplied 4.2-era cores (they failed in the original 4.3.0-pre code
    with these cores).
  - Many engine bugs fixed: lost saves on exit, a cache that evicted the newest items, stuck keys,
    startup hangs, leaked listeners and more.
  - Performance tools (addendum): live stats, performance mode, render resolution, run-ahead, audio
    latency, refresh-rate adaptation, per-game profiles and more.
  - Graphics efficiency (addendum 7): the game is drawn into a buffer the size of its picture, not
    the whole player, in whole-number steps of its own resolution: 26 to 65% fewer pixels per frame
    in tests, most on high-DPI and 4K screens.
  - Graphics efficiency (addendum 8): an opaque game surface the browser can copy or overlay instead
    of blending, without the depth and stencil buffers 2D systems never use (4 to 21 MB of video
    memory freed).
  - Web development case study, second pass (addendum 31): 15 tour stops (new: checksums, iframes
    and postMessage, one-file branding, accessibility) and 8 exercises (new: a kiosk language,
    branding your copy), with highlighted code, quiz scores and a printable handout; 38 new
    reference docs cover every page, script and tool added since round 10.
  - Classroom, second pass (addendum 30): teach step by step with a presenter bar and clocks
    (clicker keys work), end with an exit-ticket quiz, and a new lesson on binary and hex; save
    moments to come back to, watch and change bytes of memory, find the byte that holds a number,
    see a tile's bit planes and save pictures as PNG.
  - Museum and exhibit kiosk, second pass (addendum 29): visitors switch between two languages (six
    built in), read How to play, turn the sound down and get a one-minute warning; screens keep
    opening hours, dim when nobody plays and can follow the site's kiosk.json; staff order the
    games, check that every game starts and download visitor numbers per game and day.
  - Homebrew showcase, second pass (addendum 28): sort, genre and tag filters, New badges, author
    pages and a random pick; each game plays in place and has a picture viewer, credits, release
    notes, a checksum check, Add to My Collection, Download, Share and Embed; publishing writes
    link-preview share pages and an Atom feed and checks every folder more strictly.
  - My Collection, second pass (addendum 27): duplicates caught by content, games recognised from
    the showcase and archive, shelves, status and notes, your own covers, select mode with bulk
    changes and undo, list view, Continue playing, Surprise me, keyboard and controller navigation,
    and exports split into parts.
  - Build your own arcade (addendum 26): one file, site.json, sets the name, logo, colours, parts,
    systems, start page, featured games and footer of the whole site; kit.html writes it with a live
    preview and explains publishing on GitHub Pages.
  - Events and speedrun practice (addendum 25): segments with save points, a timer counted in
    console frames, practice attempts against your best, full runs with splits, personal best and
    golds, save points shared as links, and two-player races on one screen.
  - Community spaces (addendum 24): a locked-down, low-power game launcher for schools, libraries,
    shelters and waiting rooms, with opening and quiet hours, a volume limit, turns that end on
    their own, saves cleared between visitors and an offline package.
  - Accessible and comfort play (addendum 23): presets (Relaxed, Low vision, One hand, One switch)
    and options for game speed, rewind, saving, hold-to-toggle, auto-fire, one-hand keys, big
    movable touch controls, colour filters, sound captions and one-switch scanning, remembered per
    game.
  - Preservation archive (addendum 22): catalogue records for public-domain and rights-cleared
    software with provenance, licence, citation and a permanent link; CRC32, MD5 and SHA-1 checked
    in the browser; play in place; JSON, CSV and zip export.
  - Web development case study (addendum 21): a guided tour of the techniques this site uses, each
    with live values from your device and the real code, plus six exercises with hints and automatic
    checks.
  - Classroom (addendum 20): look inside a running game (palettes, sprites, background map, tiles,
    sound channels, memory, frames, input), step frame by frame, and teach six ready-made 45-minute
    lessons with worksheets.
  - Museum and exhibit kiosk (addendum 19): an unattended public screen with an attract loop, a list
    of approved games, time per visitor, a reset when the player walks away, a locked-down player, a
    staff PIN and offline play.
  - Homebrew showcase (addendum 18): new games for old consoles, each with its own shareable page,
    controls for keyboard, controller and touch, and a Play button; publish one by adding a folder
    to homebrew/.
  - Start page and My Collection (addendum 17): choose one of ten use cases or Basic; My Collection
    keeps your own games with covers and play time and moves them with their saves to another device
    in one file.
  - Load game dialog (addendum 16): the detected system and the core are shown and can be changed
    before every ROM or zip opens; zips are identified from the game file inside them, never assumed
    to be arcade.
  - 2.5D mode (addendum 15): NES and SNES games redrawn with raised, lit blocks, shadows and a
    dimmed background layer, turned on with the 2.5D button on the home page and tuned per game in
    F1.
  - iPhone and mobile review (addendum 14): pictures kept clear of the touch controls on small
    phones, ObsoleteMod fixed on phones, no layout flash, better reference docs and menus on small
    screens.
  - In-game save slot picker (addendum 13): Shift+F2 or Select+Up shows all nine quick-save slots
    with pictures and times, to save, load or delete with mouse, touch, keyboard or controller.
  - Audio efficiency (addendum 12): the audio engine is suspended while a game is paused or in the
    background (about 18% less browser CPU while paused in tests) and resumes cleanly; iPhone sound
    returns after calls or app switches.
  - Phone and iPhone view (addendum 11): a separate layout chosen from the device, portrait and
    landscape layouts that switch live on rotation, a game menu sheet, touch controls for both
    engines and iPhone home-screen support.
  - Reference docs (addendum 10): one explained page for every file, with a filterable viewer
    (reference.html), linked from the home page and the Links page.
  - A third front end, ObsoleteMod (addendum 9): the Emu retro game shelf, reached from the new
    Links page and running on the same local engine and cores.
  - Two engines to choose from when the site opens: EmulatorJSMod (the full EmulatorJS player) and
    NostalgistMod (Nostalgist.js adapted to the same local cores, with a toolbar and persistent
    saves).

2. HOW TO USE THIS EDITION
====================================================================================================

Running it
----------
  - GitHub Pages: upload the whole folder (including data/cores/*.7z) to a repository, then Settings
    > Pages > Deploy from a branch > main / root.
  - On your own PC: double-click start-windows.bat (needs Python), or run: python3 serve.py 8000,
    then open http://localhost:8000.
  - Opening index.html directly from disk (file://) does not work; the page shows a message
    explaining this.

Adding games
------------
  - Put ROMs or zips into data/A2600, data/GB, data/GBC, data/GG, data/NES, data/SNES or data/N64.
  - On GitHub the game lists update automatically after each push (GitHub Actions workflow update-
    indexes.yml). Locally, new files appear at once when you use start-windows.bat or serve.py;
    otherwise run: node tools/generate-rom-index.mjs.
  - Another platform: add a folder and a line to data/platforms.json (folder, label, short name,
    EmulatorJS system id).
  - Only add games you have the right to share: a GitHub Pages site is public.

Playing
-------
  - Pick an engine when the site opens (EmulatorJSMod or NostalgistMod); change it with Change on
    the home page or the Engine dropdown on the game page.
  - Click a game in the Game library, a Recent game, or drop a file. The game opens on play.html.
  - Switch games with the Platform and Game dropdowns at the top; Home returns to the start page.
  - On a phone the game page has a menu button (or a handle at the top in landscape) with saves,
    game choice, engine and on-screen controls; on iPhone use Share > Add to Home Screen for full
    screen.
  - Open links.html (Links on the home page or the game page) for every part of the site, including
    ObsoleteMod.
  - Open play.html (or Open the library in the player on the home page) to browse every game in the
    folders inside the player, with either engine.
  - To run the web development tour with a class, open devtour.html, press Print the exercises for a
    handout, and let students move with ← and →; Start over clears a shared computer's progress.
  - To teach with the presenter, open a lesson in classroom.html and press Start teaching; Next (or
    a clicker's Page Down) moves through the plan and runs each Show me. Save moment under the game
    keeps a point to come back to; in the Memory view, click a square to watch a byte and Set to
    change it.
  - To run a kiosk in two languages or set opening hours, open the kiosk settings (five taps in the
    top-left corner and the PIN), choose a second language and add opening-hours rows; press Check
    every game before opening, and Download visitor numbers (CSV) for the figures.
  - To share a homebrew game, open its page and press Share (the link shows a preview with the
    picture once the site's public address is set in kit.html), or Embed to put the game on another
    site; Add to My Collection keeps a copy in this browser.
  - To brand the site, open kit.html, pick a starting point, change the name, colours, parts and
    featured games while watching the preview, download site.json and put it at the top of the site
    (the guide on the page covers GitHub Pages).
  - To practise a speedrun, open practice.html, add segments, press Set start here at the start of
    each, then Practise and press . at the end of the segment; Full run times the whole route, and
    Race puts two players side by side.
  - To set up a community game corner, open community.html, choose the games, hours, volume limit
    and a PIN, press Prepare this device (or Download offline package for a laptop without
    internet), then Open the games.
  - To play with comfort options, open comfort.html, choose a game and a preset, then adjust
    anything in the panel; for one-switch play connect a switch that sends Space or Enter (or tap
    the game, or use any controller button).
  - To catalogue software, add archive/name/record.json (see archive/README.md), run npm run archive
    once to record its checksums, and push; the record page is archive.html?id=its-id.
  - To learn how the site works, open devtour.html and follow the tour; then do the exercises in a
    local copy (python3 serve.py) and press Check my work after each.
  - To teach a lesson, open classroom.html, pick a lesson, press Teach this lesson and follow the
    plan; Show me buttons load Sprite Lab or Palette Explorer and open the right view, and Print
    worksheet gives the student sheet (Print answer key for the teacher copy).
  - To run an exhibit screen, open kiosk.html, choose the games, the times and a staff PIN, press
    Prepare for offline and then Start kiosk; staff return to the settings with five quick taps in
    the top-left corner (or Ctrl+Shift+K) and the PIN.
  - To publish a homebrew game, run node tools/new-homebrew.mjs with the ROM, a title, an author and
    a licence, or add homebrew/name/game.json by hand, then push; the workflow rebuilds the showcase
    list.
  - The site now opens on the start page: choose Basic for the player as before, or My Collection to
    build your own library.
  - When you open a ROM or zip, check the system and core in the Load game dialog and press Start
    game; tick “Use this core for every ... game” to keep a core.
  - Press the 2.5D button on the home page to play NES and SNES games in 2.5D; Shift+F8 in game
    switches between 2.5D and the flat picture.
  - Shift+F2 (Select+Up on a controller) opens the save slot picker with a picture of each save.
  - In game press F1 for all hotkeys: F2 save, F3 slot, F4 load, Shift+F4 undo load, F5 pause,
    Shift+F5 reset, F6 fast forward, F7 slow motion, F8 screenshot, F9 mute, Shift+F9 performance
    mode, F10 FPS, Shift+F10 performance stats, F11 fullscreen. On a controller hold Select and
    press R1 / L1 / R2 / L2 / Start.

4. ROUND 5: TWO ENGINES, EMULATORJSMOD AND NOSTALGISTMOD
====================================================================================================

Engine choice
-------------
  1. When the site opens, a dialog asks which engine to use: EmulatorJSMod or NostalgistMod. The
     question is asked once per browser session; "Remember my choice" stops it. The home page shows
     the current engine with a Change button.
  2. The game page has an Engine dropdown that restarts the current game with the other engine;
     links between games keep it.
  3. A file dropped while the question is open waits for the answer.
  4. engines/EmulatorJSMod.js is the entry point for the existing engine (data/loader.js +
     data/src).

NostalgistMod (engines/NostalgistMod.js, source and build script in tools/nostalgist-mod)
  5. Built from the Nostalgist.js source (MIT) with no CDN access at all: cores are read from
     data/cores/*.7z and unpacked with the site's own 7z worker; the CDN ROM and shader lookups and
     the zip.js download are removed.
  6. Runs the EmulatorJS core builds as they are: a loader for their EJS_Runtime module format and
     Module.parent.
  7. Input bridge: these builds take input through simulate_input, not RetroArch's keyboard driver,
     so keyboard (Nostalgist's default bindings), gamepads (standard layout, left stick also as
     d-pad, analog sticks) and press() / pressDown() / pressUp() are routed there. Held buttons are
     released on blur and when the tab is hidden.
  8. Save and load state use the builds' in-memory state functions; screenshots read the builds'
     fixed screenshot path.
  9. A File passed to Nostalgist keeps its name (it became data1.bin, which broke patches and
     cue/bin sets).
  10. Only single-threaded core builds are used (Nostalgist does not start pthreads); PSP and DOS
      show a message with a button to switch to EmulatorJSMod.

NostalgistMod player on the game page (assets/nostalgist-player.js)
-------------------------------------------------------------------
  11. Toolbar: Pause/Resume, Reset, Save state, Load state, Screenshot, Fullscreen, Exit.
  12. Hotkeys F2 save, F4 load, F5 pause, Shift+F5 reset, F8 screenshot, F11 fullscreen (same as
      EmulatorJSMod).
  13. In-game saves (SRAM) are restored on start and written every 30 s, when the tab is hidden and
      on exit; save states are kept per game. Both live in IndexedDB ("NostalgistMod-saves").
  14. Patches, BIOS files and zipped ROMs work as with EmulatorJSMod; the canvas follows the player
      size; sound starts on the first click or key press.

====================================================================================================
5. ROUND 4: GAME LIBRARY FOLDERS AND GAME PAGE
====================================================================================================

Game library folders
--------------------
  1. New folders data/A2600, data/GB, data/GBC, data/GG, data/NES, data/SNES and data/N64 for ROMs
     and zips.
  2. data/platforms.json maps each folder to its system; add a line and a folder to add another
     platform.
  3. The home page lists the games in those folders after the core list has loaded, and only for
     platforms whose cores exist.
  4. tools/generate-rom-index.mjs writes data/<FOLDER>/index.json, because GitHub Pages cannot list
     folders.
  5. .github/workflows/update-indexes.yml regenerates the game lists and the core manifest on every
     push, so games uploaded through the GitHub website appear without running anything locally.
  6. On a local server that lists folders (serve.py, start-windows.bat) new files appear without
     regenerating the index.

Game page (play.html)
---------------------
  7. Every game now opens on its own page with a Home link and the game name.
  8. A Platform dropdown (folders with games, plus Recent games) and a Game dropdown switch to
     another game in one step.
  9. Files opened from your device are stored with their BIOS and patch, so the game page (and a
     reload of it) can open them.
  10. A BIOS or patch chosen under Options also applies to the next game opened from a library link.
  11. Exiting the game, or "Back to menu" after an error, returns to the home page.

Home page
---------
  12. Every option, section and button has a three-sentence explanation on hover, on keyboard focus,
      or by tapping its "?" badge.
  13. "What's changed from the original EmulatorJS" opens ENHANCEMENTS.txt, a full list of the
      changes.

Fixes found while building this
-------------------------------
  14. Engine: files downloaded from a URL keep their real name ("Green Test.nes", not
      "Green%20Test.nes", and no "?v=…" suffix), so patches and companion files (cue/bin, m3u) find
      each other.
  15. Service worker: game lists and folder listings are always fetched fresh, and ROMs in the
      folders are not cached a second time (EmulatorJS keeps its own copy).
  16. The core manifest no longer contains a timestamp, so it only changes when the cores change.

6. ROUND 3: 50 ENGINE IMPROVEMENTS
====================================================================================================

Under-the-hood work in data/src (no change to how the page is used).

Saves and data safety
---------------------
  1. On exit, IndexedDB saves are flushed (syncfs) before /data/saves is unmounted; the last in-game
     save could be lost before.
  2. In-game saves are written when the tab is hidden (mobile browsers often close hidden tabs
     without unload events).
  3. Loading saves from IndexedDB can no longer hang startup: errors and a 10 s timeout fall back to
     in-memory saves with a warning.
  4. In-game saves are not rewritten every interval while the game is paused.
  5. disableDatabases, or a browser without IndexedDB, uses no-op save-state storage instead of
     failing.
  6. Settings writes survive a full or blocked localStorage instead of throwing during page hide.
  7. Per-game settings are parsed once and cached until the next write (they were re-parsed on every
     getCore() call).
  8. A malformed per-game settings entry no longer stops volume and mute from loading.

Startup and errors
------------------
  9. The first start error is kept on screen; follow-on errors no longer overwrite the real cause.
  10. startGameError cannot throw halfway (it crashed when saved settings existed but the core had
      not loaded), so the error screen always appears.
  11. Startup failures anywhere in the download/initialisation chain now show an error instead of
      stalling on the loading text.
  12. A failed save-state download no longer leaves startup waiting forever.
  13. Core archives are validated: a missing .js/.wasm or bad core.json gives "Invalid core archive"
      instead of a crash.
  14. Missing PPSSPP assets (ppsspp-assets.zip, not in the supplied cores) no longer stop PSP games
      from starting.
  15. In-memory ROM/BIOS data that cannot be read resolves as a failed download instead of hanging.
  16. Errors in a local archive (corrupt zip/7z) are reported with the file name, labelled as game
      data, not "Game Core".
  17. Archives that contain only junk entries report "No game file found".
  18. Late progress updates after the game started no longer throw (loading text removed); errors
      recreate the text if needed.
  19. The loader finds its own path when document.currentScript is unavailable, and shows a message
      in the player box when the engine files are missing.

Loading performance
-------------------
  20. Local uncompressed ROMs are used directly: no full-file hash and no second copy in IndexedDB
      (a 700 MB disc image was duplicated before).
  21. Cache blob writes for one item happen in a single transaction, with the manifest written last
      so a partial write never looks complete.
  22. Cache blob reads issue all chunk requests in one transaction and merge into one buffer.
  23. getKeys() reads keys only; the old cursor loaded every cached chunk into memory during
      cleanup.
  24. The cache database is opened once (it was opened in parallel by every download) and the probe
      connection is closed.
  25. If the cache database cannot be opened the cache switches off and downloads continue.
  26. Cache eviction removes the least recently used items; the old loop evicted the newest items
      first.
  27. Directories created while unpacking archives are remembered instead of re-checked for every
      file.
  28. External support files download in parallel, and one failure no longer affects the others.
  29. Which cores exist locally is computed once from the manifest instead of scanning it on every
      lookup.

Input
-----
  30. Keys and buttons held while the window loses focus or the tab is hidden are released (they
      stayed pressed in the game).
  31. Buttons held on a controller that disconnects are released for that player.
  32. The emulator-hotkey input path no longer allocates an array per input event.
  33. Quick load reports an empty slot ("SLOT n IS EMPTY") instead of claiming success.
  34. Play/pause and autofire release are safe to call before the core is running.

Audio and video
---------------
  35. Suspended audio resumes on the first click, key or tap on every browser (was Safari-only,
      polling every 10 ms); the Safari prompt closes on the audio state change.
  36. Volume values are clamped to 0..1 and ignored safely before the core has loaded.
  37. The WebGL2 support probe releases its context (browsers cap live WebGL contexts).
  38. iPadOS (desktop user agent) and browsers with UA client hints are detected as mobile.
  39. Screenshots use a valid image type (jpg becomes image/jpeg, unknown types fall back to PNG); a
      failed encode retries as PNG.
  40. RetroArch-source screenshots time out after 5 s and fall back to the canvas instead of polling
      forever.
  41. The player reacts to container size changes (ResizeObserver), not only window resizes.

Engine structure
----------------
  42. Event handlers are isolated: one failing on() handler no longer stops the rest (or the game
      start).
  43. off(event, handler) added.
  44. Exit tears everything down: all DOM listeners (826 in a SNES session), timers, gamepad polling
      and the resize observer.
  45. Only the ROM download renames config.gameUrl; a BIOS or patch passed as data used to overwrite
      it.
  46. getBaseFileName and saveInBrowserSupported handle a File ROM (they threw on .startsWith).
  47. Core options: configured defaults are always written, saved values override by exact key (a
      saved foo_bar used to hide the default for foo), and empty values are quoted.
  48. RetroArch config values are stripped of quotes and line breaks so a value cannot break or
      inject config lines.
  49. Multi-disc playlists sort naturally ("Disc 2" before "Disc 10") and no longer require names
      that start with a digit.
  50. Routine logs only appear in debug mode (core download, extraction choices, repeated gameId
      warning).

Also fixed in the launcher: a file picked in the first seconds of a first visit could be lost to the
one-time
service-worker reload; it now waits for setup, and that reload never happens under a running game.

8. ROUND 1: EFFICIENCY REWRITE FOR LOCAL HOSTING (20 CHANGES)
====================================================================================================

Local-only build of 4.3.0-pre for static hosting. Behaviour is unchanged unless listed here.

  1. No CDN use: the CDN core fallback, the update check and the "download minified files" hints are
     gone.
  2. Cores load from data/cores/<core>[-thread][-legacy]-wasm.7z exactly as built (no renaming to
     .data).
  3. The per-core reports/*.json request is gone. The reports are not part of the supplied cores, so
     it returned 404 on every launch, and the random fallback version it then used meant the cached
     core was never found: the core was downloaded and unpacked again each time.
  4. data/cores/manifest.json (generated by tools/generate-core-manifest.mjs) lists the cores that
     exist, their extensions and WebGL2 defaults. Variant selection falls back across thread/legacy
     builds that are present.
  5. loader.js imports emulator.js directly instead of probing for a .min file, and fetches script,
     styles, language pack and manifest in parallel.
  6. Netplay, socket.io and the license text are loaded on first use (about 170 kB less at startup).
  7. IndexedDB: one shared connection per database instead of opening a new, never-closed connection
     for every call.
  8. IndexedDB: getAll/getKeys use a single cursor, and the racy ?EJS_KEYS! read-modify-write index
     is no longer maintained.
  9. Cache keys use a word-wise 32-bit hash (about 22 ms for 10 MB) instead of a per-byte loop.
  10. Cache put checks for an existing entry without loading its blobs; get no longer waits on the
      access-time write.
  11. Downloads fill a pre-sized buffer (no chunk list + Blob + copy) and report progress once per
      percent.
  12. sw.js caches the app and recently used cores for fast repeat visits and offline use.
  13. sw.js adds COOP/COEP headers so threaded cores work on GitHub Pages.
  14. Gamepad polling follows display frames while a pad is connected and idles at 2 Hz otherwise
      (was a 100 Hz timer with per-poll allocations).
  15. Core script and wasm blob URLs are created once and released; locateFile no longer leaks a URL
      per call.
  16. Decompression worker scripts are fetched once and reused, workers are terminated when done,
      and worker errors now surface instead of hanging.
  17. ROM, BIOS, save state, parent and patch downloads run in parallel.
  18. Window resize is throttled to one run per frame; fullscreen changes now actually re-run the
      resize handler (the old code only called .bind).
  19. Settings are written to localStorage after a short debounce and when the page is hidden.
  20. getCores() no longer mutates the shared table (on iOS Safari it reversed the N64 core order on
      every call).

Also: new index.html (system picker limited to available cores, whole-page drag and drop, exit
returns to the
menu), cache manager no longer throws when the cache is disabled, .gitignore no longer excludes
data/cores,
and upstream CI/dev-container/packaging files were removed.

ADDENDUM (ROUND 6): 15 PERFORMANCE FEATURES AND FOLDER GAMES IN BOTH ENGINES
====================================================================================================

Performance features in EmulatorJSMod (data/src/performance.js)
---------------------------------------------------------------
  1. Live performance stats, Shift+F10: emulation speed in % of full speed, frame time average and
     worst, late frames, display refresh rate, render resolution, graphics chip and WebGL version,
     core build, JS memory and startup time.
  2. Startup timing: how long the core download, the game load and the boot took, shown in the stats
     and the F1 panel (and in the console with ?debug=1).
  3. Slow-game detector: after a warm-up, a game that runs below 90% speed for 10 seconds offers
     performance mode once.
  4. Performance mode, Shift+F9 or the F1 panel: one switch for features 5 to 7, on and off while
     playing.
  5. Render resolution 100%, 75% or 50%: RetroArch draws into a smaller buffer that is stretched to
     the same size on screen, which cuts the GPU work on weak or very high-resolution screens. Mouse
     cores always use 100%.
  6. Automatic frameskip: in performance mode, cores that offer a frameskip option are set to auto
     (or 1), and back again.
  7. Shader bypass: in performance mode the chosen shader is switched off and restored afterwards.
  8. Low-latency canvas: the game canvas is created with a desynchronized WebGL context, so frames
     reach the screen without waiting for the page compositor (less input lag where the browser
     supports it).
  9. Run-ahead (optional, off by default): RetroArch's single-instance run-ahead of one frame
     removes a frame of built-in game lag at the cost of extra CPU. Skipped in performance mode.
  10. Refresh-rate adaptation: the display rate is measured at start; on 120, 180 and 240 Hz screens
      RetroArch presents every 2nd, 3rd or 4th refresh so 60 fps games keep their normal speed and
      smooth pacing.
  11. Audio latency choice: Low 32 ms, Normal 64 ms, Safe 96 ms or Stable 128 ms (was fixed at 64
      ms). Lower is more responsive, higher stops crackling on slow devices.
  12. Software graphics warning: when the browser draws WebGL in software (SwiftShader, llvmpipe,
      Basic Render Driver), a message explains how to turn on hardware acceleration and offers
      performance mode.
  13. Per-game performance profiles: every setting above is saved per game, and a new game starts
      with the settings used last.
  14. Core prefetch: pointing at (or tabbing to) a game on the home page or in the player's library
      downloads its core in the background, so it is cached when the game starts. Skipped with data
      saver or on 2G connections.
  15. Low-battery power saver: on battery at 20% or less, performance mode turns on for the session,
      with a button to undo.

The F1 panel has a new Performance section with these settings. Run-ahead, audio latency, low-
latency canvas and the refresh-rate adaptation apply from the next game start (RetroArch reads them
at boot); the others apply at once.

Folder games in both engines
----------------------------
  16. play.html without a game opens the game library inside the player: once the chosen engine and
      the core list are loaded, every ROM and zip in data/A2600, GB, GBC, GG, NES, SNES and N64 is
      listed by platform and starts with one click, in EmulatorJSMod or NostalgistMod. Platforms the
      engine cannot run are shown disabled with the reason.
  17. play.html?folder=NES lists one folder; adding &autoplay=1 starts its first game.
  18. The home page loads the chosen engine before listing the folders, marks platforms that engine
      cannot run, links to the library in the player, and lists the folders again when the engine is
      changed.
  19. Only real game files count: a folder's ROM extensions plus zip and 7z. Readme files, cover
      art, saves and patches dropped into a folder no longer appear as games.
  20. Two files with the same title (game.nes and game.zip) show their type in the library.
  21. NostalgistMod requests cores with the same address as EmulatorJSMod (with ?v=), so both
      engines and the prefetch share one cached download.

ADDENDUM (ROUND 7): PICTURE-SIZED RENDER BUFFER FOR GRAPHICS EFFICIENCY
====================================================================================================

One change to EmulatorJSMod (data/src/performance.js), on by default
  1. What it changes: RetroArch makes its drawing buffer as large as the canvas box. EmulatorJS made
     that box the whole player area, black bars included, at the screen's full pixel density. A
     256×224 SNES game in a 1000×555 player on a 2× (Retina / high-DPI) screen was drawn into a
     2000×1112 buffer: 2.2 million pixels per frame, about a third of them black bars. Now the
     canvas box is exactly the game's picture, and on screens with enough pixels the buffer is a
     whole multiple of the game's own lines (×3 or more). The browser's compositor scales that
     buffer the last step to the picture size.
  2. Measured (Chrome, SNES at 60 fps): 1× screen 1000×555 buffer → 740×555 (26% fewer pixels); 2×
     screen 2000×1112 → 1195×896 (52% fewer); 1920×1080 window with the NES test ROM 1920×882 →
     878×672 (65% fewer). A 4K full screen drops from about 8.3 to 5.4 million pixels per frame for
     a 224-line game.
  3. Why it is faster: every frame RetroArch clears, draws and presents fewer pixels, the WebGL
     buffer uses less video memory, and the browser has less to copy to the screen. This matters
     most on laptops and phones with high-density screens, integrated graphics, 4K monitors and full
     screen.
  4. How the picture looks: the black bars are drawn by the page instead of the game. With the
     whole-number step, every game pixel is the same size (no uneven rows or shimmer when the screen
     scrolls); the browser's final smooth step of at most about 1.33× softens edges very slightly.
     When the picture has fewer than three screen pixels per game line, the buffer keeps full
     resolution and only the bars are removed, so a small player on a 1× screen looks exactly as
     before.
  5. Follows the game: the layout is recalculated when the player is resized, on full screen, when
     the game changes resolution (menus, hi-res and interlaced modes, PAL/NTSC) and when the video
     rotation changes.
  6. Works with the other performance features: render resolution and performance mode scale this
     smaller buffer further (performance mode on a 2× screen gives ×3 lines, 896×672).
  7. Kept at full size where it matters: with a shader chosen the buffer keeps every screen pixel of
     the picture (CRT and scanline shaders need them; the bars are still left out); mouse and light-
     gun cores keep the original canvas so pointer positions stay exact.
  8. Where to see it: Shift+F10 stats show a new Buffer line, e.g. "picture only, x4 lines, 52%
     fewer pixels than 2000×1112"; the F1 panel's Performance section shows the same and has a
     "Picture-sized render buffer" switch (saved per game) to compare with the old behaviour.
     Screenshots work as before.

ADDENDUM (ROUND 8): LEAN OPAQUE GAME SURFACE FOR GRAPHICS EFFICIENCY
====================================================================================================

One change to EmulatorJSMod (data/src/performance.js), on by default
  1. What it changes: the WebGL surface the game is drawn on is now created opaque (alpha off) and,
     for 2D cores, without the depth and stencil buffers. EmulatorJS created it the WebGL default
     way: transparent (alpha on, premultiplied), plus a 24-bit depth and an 8-bit stencil buffer the
     size of the screen surface.
  2. Why the transparent surface cost work: the browser had to treat the game as a see-through layer
     and blend every pixel of it with the page below, every frame. An opaque layer is simply copied,
     and Chrome, Edge and Safari can hand an opaque canvas to the GPU's hardware overlay (direct
     scan-out), skipping the page compositing step completely in full screen.
  3. Why depth and stencil were waste: NES, SNES, Game Boy, Game Boy Color, Game Gear, Atari 2600
     and every other 2D core draws its finished picture as one flat image; RetroArch's menu and
     shaders work in their own buffers. The two buffers cost 4 bytes of video memory per pixel: 4.3
     MB at 1195×896, 8.9 MB at the old full-player 2000×1112, about 21 MB in 4K full screen, all
     freed. They no longer have to be resolved or cleared each frame either.
  4. 3D cores keep both buffers: Nintendo 64 (mupen64plus_next, parallel_n64), PSP, DS, Dreamcast,
     Saturn, 3DS, hardware PlayStation renderers and DOS, plus any core whose name ends in _hw or
     gl. A site owner can keep them for every core by setting keepDepthBuffer: true in the
     EmulatorJS config.
  5. Measured (Chrome with software graphics, SNES with the CRT Easymode shader at 2× density, the
     heaviest case available here, two runs each): 16.1 fps with the old surface, 16.9 fps with the
     lean one, about 5% faster with nothing else changed. Without a shader both run at a full 60
     fps; on a real graphics chip the gain shows as lower GPU load and power use rather than higher
     fps.
  6. Nothing looks different: the game picture, shaders, screenshots, save states and the black bars
     around the picture are unchanged (checked by reading back screenshots with and without a
     shader).
  7. Where to see it: Shift+F10 stats have a new Surface line, e.g. "opaque, no depth/stencil (2D
     core)" or "depth/stencil kept (3D core)"; the F1 panel's Performance section shows it too and
     has a "Lean opaque game surface" switch (saved per game, applies from the next start) to
     compare with the old surface.

ADDENDUM (ROUND 12): IDLE AUDIO SUSPENSION FOR AUDIO EFFICIENCY
====================================================================================================

One change to EmulatorJSMod (data/src/performance.js, plus a pause/play event in
data/src/emulator.js), on by default
  1. What it changes: RetroArch plays sound through a WebAudio context (Emscripten's OpenAL).
     EmulatorJS created it once and left it running for the whole session, so the browser's audio
     thread and the device's audio output kept working at full rate (44.1 or 48 kHz, hundreds of
     wake-ups a second) even when the emulator had stopped producing sound. Now the context is
     suspended whenever no sound can come out, and resumed when play continues.
  2. When it suspends: the game is paused (F5, the F1 panel, the phone game menu, auto-pause when a
     controller disconnects) or the tab or app is in the background. It does not suspend while a
     game runs muted, because RetroArch then still feeds the audio queue and would wait for room.
  3. Why sound comes back cleanly: the context is suspended, not closed, so the sound already queued
     is kept and playback continues from the same point. There is no skip, no burst of queued sound
     and no new audio setup on resume.
  4. Measured (headless Chrome, SNES game paused for 10 seconds, three runs each): the browser used
     45 to 50 units of CPU time with the context suspended against 55 to 58 with it running, about
     18% less while paused, and the audio clock stopped advancing (0.00 s instead of 3.00 s over 3
     seconds). On real hardware the larger saving is that the audio device can go idle, which most
     matters for laptops and phones on battery.
  5. iPhone and iPad: Safari stops audio during calls, Siri or when you switch apps (the
     "interrupted" state) and the old code never restarted it, so the game came back silent. When
     the game is visible and running again the context is resumed, and if Safari needs a tap first,
     the next tap or key press brings the sound back.
  6. Where to see it: Shift+F10 stats have a new Audio line, for example "44100 Hz, suspended
     (paused), idle audio stopped for 3 s", and the F1 panel's Performance section has a "Stop audio
     processing while paused or hidden" switch (saved per game) to compare with the old behaviour.
     Pausing and resuming, save and load states, fast forward and mute work as before.

ADDENDUM (ROUND 15): 2.5D MODE FOR NES AND SNES
====================================================================================================

2.5D view (data/src/depth25.js, EmulatorJSMod)
----------------------------------------------
  1. A 2.5D button on the home page (next to the engine) turns 2.5D mode on or off; it is
     remembered, applies to NES and SNES games, and ?depth25=1 or ?depth25=0 on a game address
     overrides it for one game. With 2.5D on, NES and SNES games always start in EmulatorJSMod,
     which draws the effect.
  2. How it looks: every frame is redrawn as a scene with depth. The colours that fill most of the
     screen (the backdrop, sky bands, a checkerboard) become a dimmed far layer; everything else
     (level tiles, platforms, characters, items, text) becomes raised blocks, one per game pixel,
     each with a lit top face above it, a light top edge, darker right and lower edges, and a soft
     shadow cast down and to the right onto the far layer, with shading where blocks meet it.
  3. Backdrop colours are worked out from the picture several times a second, so the layering
     follows the game from screen to screen without any per-game setup.
  4. Gameplay is untouched: the emulator, timing, input, saves, screenshots (F8 saves the flat game
     picture) and every other feature run as before; 2.5D only changes how the finished frame is
     shown, on a second canvas laid exactly over the game.
  5. Adjustable while playing: Shift+F8 switches between 2.5D and the flat picture, and the F1 panel
     has a 2.5D section with Block height, Shadows, Background brightness and Highlights sliders,
     saved per game. The phone game menu has a "2.5D view" switch.
  6. Keeps the game at full speed: the effect is computed in two GPU passes (one at the game's own
     resolution, one on screen). If frames start taking longer than the screen's refresh, it draws
     with fewer pixels (4, 3, then 2 per game pixel) and remembers the level for that device.
  7. Limits: the depth is worked out from colours, not from the game's own layers (a browser
     emulator cannot see those), so it does not reproduce hand-made 3D remakes of particular games.
     Games with a plain backdrop (most NES games) show the clearest layering; very detailed SNES
     backgrounds are partly raised along with the foreground; the sliders tune the result per game.

ADDENDUM (ROUND 16): SYSTEM AND CORE CHOSEN BEFORE A GAME FILE OPENS
====================================================================================================

Why: opening a zip with an N64 game could start it as an arcade game on the wrong core (FinalBurn
Alpha 2012 CPS-1). Three things caused it: a zip was treated as arcade whenever its contents could
not be read by name; the system picker remembered one answer per file type ("Remember for this file
type" was ticked by default), so after one arcade zip every later zip went to arcade without asking;
and a 7z was always taken for arcade.

  1. Load game dialog: every ROM or zip opened on the home page (drop, file picker, Open file on
     phones) now shows the system it was detected as, how it was detected, and the emulator core
     that will run it, before anything starts. Both can be changed; Start game opens it, Cancel
     stops. When the system can't be told, the dialog asks for it and Start game waits until one is
     chosen.
  2. Zips are read properly: the dialog looks inside the zip, decompresses the start of the largest
     file and checks its header, so an N64, NES, SNES, Game Boy, GBA, Mega Drive, Master System/Game
     Gear, Lynx or 7800 game is recognised even when the file inside has an odd name such as
     rom.bin; readme, picture and save files in the zip are ignored. File types inside the zip are
     the fallback.
  3. Archives are never assumed to be arcade: a zip or 7z whose contents can't be identified asks
     for the system instead of picking arcade.
  4. The old per-file-type answers ("every .zip is arcade") are deleted on the first visit after
     this update.
  5. Core choice: the dialog lists the cores installed for the system (the default first) with a
     short note on each (for example "Mupen64Plus-Next: best compatibility", "FinalBurn Alpha 2012:
     Capcom CPS-1 arcade boards only"), and marks cores that need threads or that NostalgistMod
     cannot run. "Use this core for every <system> game" remembers the choice; it is then also used
     for games opened from the library folders, the player's library and links.
  6. The chosen core really is used: it is stored with the game in Recent games and passed to the
     engine, and it takes priority over a core saved earlier in the EmulatorJS settings menu (which
     previously overrode it). play.html?url=...&core= also accepts a core name (for example
     &core=parallel_n64) as well as a system.
  7. Threads follow the chosen core: a core that needs threads is only required when that core is
     picked.

For visitors:
-------------

- Languages. Visitor text is built in for English, Español, Français, Deutsch, Italiano and
Português.
- Staff choose the screen's language and, optionally, a second one.
- With two languages, the attract loop takes turns between them. A language button on the attract
loop and the
game list switches language, and a visitor who wakes the screen gets the language that was on show.
- Each game can have a caption and How to play in both languages. The title and call to action can

- How to play. Each game has a short How to play text, shown while it starts and behind a How to
play button

- Sound button. Visitors can turn the sound down or off. It is never louder than the staff's volume,
and it is
reset for each visitor.
- One-minute warning. With a time limit over two minutes, a "one minute left" message appears
without pausing
the game.
- Opening hours. Rows of days and times, overnight included. Outside them the screen is dark and
shows when it
opens again. A visitor playing at closing time gets a short goodbye. Touches do nothing while
closed, but the staff
gesture still works.
- Dimming. After a set time without visitors (30 minutes by default, 0 for never), only the call to
action
stays, dimmed. It moves now and then to avoid screen burn-in, as the closed screen's text does. A
touch wakes it.
- On phones, the in-game buttons shrink to their symbols so they fit in one row.

For staff:
----------

- Game order. "On this screen, in this order" lists the ticked games with Move up, Move down and
Remove. The
captions and How to play are edited there.
- Check every game. Starts each approved game once in a hidden, silent player and reports which ones
started and
how long they took. The last result is kept.
- Settings left open. After five minutes without a touch, the settings close and the screen goes
back to the
attract loop with the saved settings.
- Visitor numbers are kept per day (60 days), per game and per hour.
- The status shows the busiest hour today and a 14-day table with the most played games.
- Download visitor numbers (CSV) writes them for a spreadsheet.
- The old totals for today carry over.
- Follow the site's kiosk.json. A screen with this ticked checks the file at start and every half
hour, and uses
any change between visitors (never during a game). A PIN in the file wins, so many screens can be
managed from one
file. A new screen that starts from a kiosk.json with "managed": true follows it from then on.
- The status also shows opening hours (open or closed, and the next change) and where the settings
come from.

Engine side: the kiosk player (play.html?kiosk=1) obeys a new "volume" message. The shared game list
